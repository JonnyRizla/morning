- **libghostty returns null, not 0x1, for empty output** (github, 2026-09-07) [link](https://github.com/ghostty-org/ghostty/commit/b0c421fcd2e290629d4285c181b52fe2f2095f06)

- **A config clone that borrowed its source's strings** (github, 2026-09-07) [link](https://github.com/ghostty-org/ghostty/commit/623106cc4ea9ad5b8cc070e5e5c5260eb6eeaa7b)
  `RepeatableCommand.clone` copied `value_c` shallowly, so a cloned config's `Command.C` structs kept string pointers into the *source* config's memory — the one field in an otherwise deep copy that silently borrows. The macOS app never noticed, because its clone's source is the core-owned live config and both are replaced together on reload. An embedder that clones a config and then frees the source, a legal sequence when promoting the clone to active, reads freed memory the next time it fetches `command-palette-entry` through the C API. AddressSanitizer caught it while testing the Windows embedding host.

  He traced the history in the commit: `dbe6035da` introduced `RepeatableCommand` with a correct deep clone, and `017021787` added the `value_c` mirror but extended `clone` with only a mechanical `ArrayList.clone` — the structs copy, the string ownership does not. Nothing in-tree exercises clone-then-free-source, so it stayed latent from the day the C exposure landed.

  The charter's stated mission is to make MCP Resources bidirectional, so an agent can write a result back to the server it read its inputs from. - **Graphiti was leaking episodes between tenants under concurrency** (github, 2026-09-08) [link](https://github.com/getzep/graphiti/commit/08834609936e85a1bbed4158773b1f4641f48d6f)
  `add_episode` and `add_episode_bulk` reassigned the shared `self.driver` whenever a `group_id` mapped to a different database. Because those coroutines contain many await points — LLM calls, embeddings, database reads and writes — a concurrent call for a different `group_id` could reassign `self.driver` mid-execution, after which the first call's remaining operations targeted the wrong database. The commit says this showed up in production as episodes leaking across FalkorDB group graphs with no error raised.

  The fix replaces the shared-state mutation with `_resolve_request_scope(group_id)`, returning the effective group id, a per-call driver and a matching `GraphitiClients` copy, then threads that bundle through both entry points and six helpers rather than letting them read `self.driver`. Worth knowing if you run Graphiti multi-tenant: this is a silent-corruption class of bug, and it is fixed on main rather than in a release — the newest tag is still v0.30.0 from 1 September.

- **A FalkorDB search that took 33 seconds now takes 1.6 milliseconds** (github, 2026-09-08) [link](https://github.com/getzep/graphiti/commit/2d96f27138d21b723d6ad4f21fc9e0422f29e94e)
  `edge_fulltext_search` resolved a matched relationship's endpoints with `MATCH (n:Entity)-[e:RELATES_TO {uuid: rel.uuid}]->(m:Entity)`. FalkorDB plans that as a Node By Label Scan over every `:Entity` node for each row the fulltext index yields, so the search costs O(hits × entities) even though a trailing LIMIT keeps only a handful of rows. The commit includes the query plan showing the label scan nested once per hit.

  The relationship the index already returned knows its own endpoints, so the fix reads them with `startNode()`/`endNode()` and keeps an added label predicate to hold the result set identical. Measured on a graph of 5,665 nodes, 20,263 `RELATES_TO` edges and 3,725 entities, returning a byte-identical 306-row result: 33,383 ms before, 1.6 ms after. Eleven lines, one file. Neo4j and Kuzu are untouched.

- **A reranker that ranked backwards, and four other landed fixes** (github, 2026-09-08) [link](https://github.com/getzep/graphiti/commit/3ff5c160c57c6790aeb148e7388bf380ed351c7b)
  The pick of this batch is `episode_mentions_reranker`, which sorted by MENTIONS-edge count ascending — so entities mentioned in the fewest episodes ranked first, the opposite of the name and of every other count-based reranker in the codebase. The root cause was a borrowed convention: unmentioned nodes got a `float('inf')` sentinel taken from a distance-based reranker, where "no path found" correctly means worst. Under mention-count semantics that made an unmentioned node always satisfy `score >= min_score`, so a positive `min_score` could never filter out zero-mention nodes — the one case it exists for. Now it sorts descending with a sentinel of 0.

  The rest: FalkorDB datetime params normalized to UTC, entity labels applied in one query during bulk save instead of persisted as a node property, and a saga re-fetch that selected only four columns so `first_episode_uuid` and `last_episode_uuid` came back `None`, making every `add_episode` re-fire the first-episode guard.
