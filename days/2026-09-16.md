- **Datasette gets supervised background tasks, a `shutdown()` hook and a documented lifecycle** (github, 2026-09-15) [link](https://github.com/simonw/datasette/commit/0c317785806df88cc27ad59c0d083c8e3df816f8)
  `datasette.add_background_task(func, name=None)` registers a coroutine taking the `Datasette` instance, and core launches it only after *every* `startup` hook has finished — so a task registered by one plugin can depend on state another plugin set up. Core then owns it: a strong reference is kept so it cannot be silently garbage collected the way an unreferenced `asyncio.create_task()` can; anything other than `CancelledError` is logged to the `datasette.background_tasks` logger and moves `.state` to `crashed`; on shutdown every running task is cancelled with a five-second grace period.

  Three more Alex Garcia PRs landed in the same hour: a [`shutdown()` plugin hook](https://github.com/simonw/datasette/commit/cca08d2886404afcdf98a8428c813de20ca85f58) running before tasks are cancelled and connections close (not on `SIGKILL`), a [fix so `startup()` runs before any plugin `asgi_wrapper` middleware](https://github.com/simonw/datasette/commit/784695aea6dcb6a686b2b30bb1b4e20fecd127af), and a [`/-/tasks` endpoint](https://github.com/simonw/datasette/commit/374b194ff51b66859adcff95eb13576fcb29af76) behind `permissions-debug` listing each task's `state`, `started_at` and a one-line `repr()` of its exception. The docs admit the bug this replaces: older versions ran startup on a temporary CLI event loop closed before the server's own loop existed, silently killing anything scheduled on it. `datasette-cron` and `datasette-enrichments` are being migrated off the `asgi_wrapper`-starts-a-task pattern.

- **Omarchy switches TCP congestion control to BBR with fq pacing** (github, 2026-09-15) [link](https://github.com/basecamp/omarchy/commit/f2b419d9a9d7e7821de2ddf9c42991e32cf06cdf)

- **The `retro` skill now builds a lint rule instead of writing another coding-standards line** (github, 2026-09-15) [link](https://github.com/mattpocock/skills/commit/959a8e9f1edc3adbe2f7e3054bb6fbefa6696260)
  A two-line edit to `skills/in-progress/retro/SKILL.md` with a sharp argument behind it. The commit message states the problem: retro treated every reviewer-agent gap the same way, by adding a `CODING_STANDARDS.md` line, which "just asks the reviewer agent to re-derive the same call on every future diff, forever, instead of paying once for a check". Coding standards now classifies a violation first — **mechanical** (a fixed syntactic pattern, a banned API, an import shape, a file-location rule) gets a deterministic check "full stop", whether a linter rule, a pre-commit hook or a CI job; `CODING_STANDARDS.md` is reserved for judgement calls like "matches the surrounding style".

  Automated checks gets the complementary change: read the repo's own `lint`/`check` script and CI workflow first, so "a check that already exists but sits unwired or silently broken is the finding, not a reinvention" — and a repo with no guardrail at all is itself a finding, "a standing missed opportunity, not a neutral default". Kept language-agnostic, with no ESLint or TypeScript naming, since retro runs across repos in different languages. Merged as PR #1083.

## Armin Ronacher
- **Interpreting Pangram** (blog, 2026-09-14) [link](https://lucumr.pocoo.org/2026/9/14/interpreting-pangram/)
  Ronacher tests the AI-text detector after David Sacks's tweet was flagged 100% AI and Sacks called such detectors bogus. Pangram manufactures its own training data — start from known human text, have an LLM write a fresh text on the same topic, and have it make partial edits so co-authored passages are learned; the [paper](https://arxiv.org/abs/2607.27183) claims 0.0041% false accusations and 0.34% missed AI text. He has Opus 5 generate a Sacks-style tweet from a structural prompt, which Pangram calls 100% AI. He then rewrites it by hand, paragraph by paragraph, no LLM except a typo pass — about 50% similar by similarity checkers, not one shared sentence. Pangram returns 100% AI again.

  His conclusion is about structure, not phrasing: "if you rely on an LLM to give your text structure, it will score badly on Pangram even if you do plenty of edits over it." He credits the tool for making him notice his own two-year AI-assisted blogging has drifted, the tools becoming "much more aggressive editors" — while allowing that "100% AI" reads as misleading to people who edited substantially.
