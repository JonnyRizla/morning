## Simon Willison
- **Datasette 1.0a40 gives plugins supervised background tasks and a `shutdown` hook** (github, 2026-09-16) [link](https://github.com/simonw/datasette/commit/2eb2571fee3d4cdfab4086831c7a4a0800b15174)
  The headline API is `datasette.add_background_task()`: plugins register long-lived work, typically from a `startup` hook, and every registered task is launched after all `startup` hooks have run and cancelled with a five-second grace period on shutdown. A new `permissions-debug`-gated `/-/tasks` JSON endpoint lists each supervised task and its state, in the style of `/-/threads`, and a new `shutdown` plugin hook fires on Ctrl-C or `SIGTERM` before tasks are cancelled and connections closed — but not on `SIGKILL`. `asgi_wrapper` middleware now always runs after startup completes, and the release notes tell plugins that start background work on first request to migrate; `datasette-cron` and `datasette-enrichments` are named as in-flight migrations.

  Two other changes carry breakage. There is a new POST count endpoint for counting filtered table rows, now behind the **count all** button (#2914), and Datasette has switched from `httpx` to `httpx2`, Pydantic's continuation of it, so `datasette.client` responses are `httpx2.Response` objects — plugins doing `isinstance()` checks against `httpx.Response`, or using httpx without declaring it, have to change.

- **A trailing newline in a table name bypassed table permissions; the fix is `match` → `fullmatch`** (github, 2026-09-16) [link](https://github.com/simonw/datasette/commit/caf238aac86ebe370959b25384d6e05f6a1e2359)
  `escape_sqlite()` tested identifiers against `_boring_keyword_re = re.compile(r"^[a-zA-Z_][a-zA-Z0-9_]*$")` using `re.match`, which anchors at the start only, so `"secret\n"` matched and was returned unquoted. SQLite then read the name as `secret` while Datasette's permission checks were still evaluating the string `secret\n` — a user denied `view-table` on `secret` could create a `secret\n` table, request it as `/data/secret~0A.json`, and have the query resolve to the protected table. One word changes: `.match` becomes `.fullmatch`. Reported by `dpfkdlemtp`, tracked as GHSA-h547-rmjf-5m2m.

  The regression test in `test_api_write.py` runs three operations — table read, row read, and an alter-table rename — and asserts that each one targets the decoy rather than the protected table; `test_utils.py` gains `("plain\n", "[plain\n]")` and `("select\n", "[select\n]")` cases. The same one-word fix was [backported to the stable branch](https://github.com/simonw/datasette/commit/23b76098f6dc3acd3550cf6768e4194f9140a98e) and released as 0.65.5, committed a minute ahead of the 1.0a40 release and uploaded to PyPI four minutes behind it — the second time in a week Willison has paired an alpha with a 0.65.x maintenance security release, after 1.0a39 and 0.65.4 on 11 September.

- **The table footer's "Queries took 1.2ms" was a hardcoded 1.2** (github, 2026-09-16) [link](https://github.com/simonw/datasette/commit/9cdf95ac2c47fe80bc368e2564f5554de1dc998a)
  `table_view_traced()` in `views/table.py` passed the literal `query_ms=1.2` into its template context, so every table page in the 1.0 alphas reported the same made-up timing regardless of how long the query actually took. The fix is three lines: a `time.perf_counter()` before `table_view_data()`, the elapsed milliseconds captured after it, and that value passed through instead of the constant. Closes #2446.

  The test is the more interesting half. `test_table_footer_query_ms` monkeypatches only `datasette.views.table.time` with a `SimpleNamespace` whose `perf_counter` yields `10.0` then `10.0 + duration`, leaving the real clock in place elsewhere so SQL time limits are unaffected, then asserts the footer text for both a table and a SQL view at two durations. Note the timer brackets the whole of `table_view_data`, not the SQL execution, so the number is now page-assembly time rather than query time strictly speaking.

- **Setting defaults in the docs are now generated from `DEFAULT_SETTINGS`, and a test enforces it** (github, 2026-09-17) [link](https://github.com/simonw/datasette/commit/3239d10b9bc6e9a451439995db226a39274a2f88)
  A new `docs/settings_doc.py` exposes one cog helper, `setting_default(cog, name)`, which reads `datasette.app.DEFAULT_SETTINGS[name]`, renders booleans as `on`/`off`, and emits a one-line "Default:" paragraph with the value in literal markup. `docs/settings.rst` gains a cog block per setting — 229 changed lines — and the prose is rewritten to stop repeating the number: `sql_time_limit_ms` loses "By default, queries have a time limit of one second" for "Time limit for SQL queries, in milliseconds", and `max_returned_rows` loses the hardcoded "1,000" from its first sentence.

  `test_settings_are_documented` used to assert only that each setting appeared as a heading. It now splits `settings.rst` into per-setting sections with a regex and additionally asserts that `setting_default(cog, "<name>")` appears inside the matching section, so a new setting cannot be documented without wiring its default to the registry.
