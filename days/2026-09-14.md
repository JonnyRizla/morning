## David Heinemeier Hansson
- **Omarchy switches desktops to the kyber I/O scheduler** (github, 2026-09-13) [link](https://github.com/omacom/omarchy/commit/dae1f4bf0e3f0a4c1e1a01b423e7b0f5f442d17a)
  The argument in the commit message: the kernel leaves NVMe on `none` and everything else on `mq-deadline`, and neither bounds latency once the device queue fills, so a build, copy or package upgrade makes the desktop sluggish while reads queue behind writes. Kyber keeps separate read and sync-write queues and throttles submission depth to hit a 2 ms read target, which he accepts costs a little peak throughput — a real trade for a storage server chasing IOPS, not for a desktop. It ships as a package-owned udev rule at `etc/udev/rules.d/60-omarchy-io-scheduler.rules`, so it applies at boot and on hot-plug; existing installs get it at next boot, and zram is left alone.

  Sixteen minutes later he had to narrow it: udev patterns are shell globs, so `nvme[0-9]*n[0-9]*` also matched partitions, which have no `queue/scheduler` and logged a "Could not chase sysfs attribute" error each at boot. The [follow-up](https://github.com/omacom/omarchy/commit/795ac57a6c65ed1943c62739efb228bffce048bd) matches `SUBSYSTEM=block` with `DEVTYPE=disk` instead.

- **Pacman transactions get moved out of the desktop session's cgroups** (github, 2026-09-13) [link](https://github.com/omacom/omarchy/commit/f5194e3ff596789b71b912ba945d90e3693cf6aa)
  A concrete failure mode: upgrading systemd runs its `post_upgrade` scriptlet mid-transaction, which reexecs the system manager and every user manager. Omarchy's update runs pacman inside a floating terminal, i.e. inside a user-session scope, so that reexec can SIGKILL it and abandon the transaction with packages upgraded but no post-transaction hooks run. The fix routes every Omarchy-owned system mutation — `omarchy-channel-set`, `omarchy-refresh-pacman`, `omarchy-reinstall-pkgs`, `omarchy-update-system-pkgs` — through a new hidden `omarchy-update-pacman` that wraps pacman in `systemd-run --scope --quiet --collect`, registering it under PID 1. System scopes survive the system manager's reexec, and the transaction now also survives its terminal being closed. In an installer chroot, where `/run/systemd/system` is absent, it execs pacman directly.

  Two companion commits in the same push make a presented command that exits non-zero show a failure state, and tell the user how to resume a channel switch that died partway — the same class of problem, seen from the UI side.

- **A crash-a-day core dump traced to spawning Python every two seconds** (github, 2026-09-13) [link](https://github.com/omacom/omarchy/commit/55799c4ab09f9cf9a60aed42b79f9ecf9f44bb2b)
  Omarchy's battery service ran `powerprofilesctl get` on a two-second poll to keep the active power profile visible to the wallpaper and lock services. That command is a PyGObject script, so the shell was starting a CPython interpreter tens of thousands of times a day, and roughly once a day one of those exits hit a 3.14 finalization race (cpython#124619) where the GLib D-Bus worker thread calls `PyGILState_Ensure` after teardown: SIGSEGV, core dump, crash notification. The service now reads the `ActiveProfile` property straight off power-profiles-daemon with `busctl`, matching how `omarchy-powerprofiles-set` already reads UPower. Because the output is JSON, an empty or malformed reply when the daemon is not running still reads as no active profile, so behaviour is unchanged.

  Twenty-six changed lines in `shell/plugins/services/battery/Service.qml`. A good example of the pattern he keeps hitting in this repo: the bug is not in Omarchy's logic, it is in how often Omarchy shells out.
