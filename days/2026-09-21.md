- **libghostty-vt gets a render-hold callback, because checking mode 2026 before each draw loses frames** (github, 2026-09-19) [link](https://github.com/ghostty-org/ghostty/commit/56a3437a7f51796d7946584043229c2f15c70583)
  398 insertions. Until now libghostty-vt did nothing for synchronized output beyond setting the mode bit, leaving an embedder to check the mode before every draw and skip its render-state update. Hashimoto names two failures in that: the frame left on screen is whatever was drawn last, "which can be older than what the program intended or even a half-drawn frame"; and if the program resets and sets the mode again between two draws, the mode never appears to turn off and the finished frame is lost, so a continuously drawing program looks frozen. The new `GHOSTTY_TERMINAL_OPT_RENDER_HOLD` callback fires with `held` true the instant mode 2026 is set, when "nothing after the start of the hold has been processed yet" — so updating the render state from inside it captures the frame the program wants held.

  The header is blunt about what the library will not do: "The terminal has no clock, so it never ends a hold on its own", so the embedder needs its own timeout — one second, in the worked C example — or a crashed program freezes the screen forever. His own note on the commit: "This actually is a more robust implementation than Ghostty GUI has so I plan to follow up to fix that!"

- **Mode lookup becomes a branchless binary search: 10.5ns to 3.2ns for mode 2026** (github, 2026-09-19) [link](https://github.com/ghostty-org/ghostty/commit/01a8d3af223dbb5ba3ddbf0a8f3d7820e304880a)
  `modeFromInt` compared a runtime mode number against every table entry with an `inline for`, "hundreds of branches and instructions" in disassembly, and an unknown mode paid for all of them. The replacement is a new `datastruct.ComptimeIntSet`, 172 lines: it sorts comptime-known keys and does a fixed-step binary search with no loop, so a lookup costs about log2(N) comparisons and compiles branchlessly. `indexOf` returns the key's position in the slice you passed in, not in sorted order, so it indexes any parallel table. `ModeTag` stores the number in 15 bits, so anything above `maxInt(u15)` now returns null rather than spilling into the `ansi` bit; a new exhaustive test checks all 65,536 values against a plain scan.

  The measured wins, from the commit message: get unknown mode 10.5ns → 1.8ns, `CSI ? 2026 h/l` 20.6ns → 12.7ns per sequence, set/reset three modes 46ns → 28ns, DECRQM 57ns → 41ns. He calls it "admittedly a micro-optimization" with a practical reason: the modes checked on the render path, synchronized rendering above all, are checked constantly, "and every nanosecond is something we want to save".
